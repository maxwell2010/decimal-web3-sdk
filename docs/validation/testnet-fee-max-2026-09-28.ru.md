# Повторная проверка MAX и комиссий в Decimal testnet

Дата: 2026-09-28. Сеть: testnet, chain ID 202020. Использован ранее
согласованный тестовый кошелек и его производные адреса. В майнете транзакции
не отправлялись. Сид-фраза и подписанные raw-транзакции не сохранялись в отчет.
Официальный `testnet-val.decimalchain.com` отвечал напрямую, но локальный
HTTP-прокси давал таймаут. Только для диагностического процесса узел был
исключен из прокси через `NO_PROXY`; проверка HTTPS-сертификата не отключалась.

При блоках 21974859-21974934 RPC возвращал `eth_gasPrice = 1190475000000 wei`
(1190.475 gwei), `baseFeePerGas = 1058200000000 wei` и
`maxPriorityFeePerGas = 132275000000 wei`. Для type 0 SDK использовал именно
сетевой gasPrice, без cap. Значение `fee_budget` ниже означает допустимый

Для MAX без memo баланс тестового адреса был `0.080001 tDEL`, значение
перевода `0.0525010275 tDEL`, остаток `0.0024999975 tDEL`. С memo баланс
был `0.08 tDEL`, перевод `0.052142885 tDEL`, остаток `0.0025333308 tDEL`.
Оба остатка в точности равны неиспользованному gasLimit buffer:
`(gasLimit - gasUsed) * gasPrice`. Это не списанная комиссия.

Type 2 был создан низкоуровневым API SDK только для сравнения, без изменения
публичного high-level отправителя. Текущий high-level расчет комиссии SDK
ориентирован на type 0 (`gasPrice`); приведенный type-2 upfront рассчитан
отдельно, не через `calculate_fee`. `maxFeePerGas = 2248675000000 wei`,
`maxPriorityFeePerGas = 132275000000 wei`; upfront
`23100 * maxFeePerGas + 1 wei = 0.051944392500000001 tDEL`.
В receipt `effectiveGasPrice = 1190475000000 wei`, списано
`21000 * effectiveGasPrice = 0.024999975 tDEL`. Блок освободил разницу между
максимальным резервом и фактическим расходом. В этой точке сети фактическая
цена газа у type 0 и type 2 одинакова; предположение о завышенной фактической
комиссии SDK по сравнению с type 2 не подтвердилось.

Для покупки, делегирования и hold изменение нативного баланса точно равно
`value + gasUsed * gasPrice`, без дополнительного списания. Баланс основного
тестового адреса перед этими тремя операциями был
`984.487150471111333249 tDEL`, после - `983.780126175136333249 tDEL`.

Дополнительная проверка суммы без отправки: строка `6.808` стала
`6808000000000000000 wei` и в черновике, и в реально подписанном raw type 0.
SDK не применял float и не превратил значение в `6.80799...`. Для объяснения
такого отображения в Console нужен хеш конкретной пользовательской
транзакции и сравнение ее поля `value` с введенной суммой.

## Вывод для MAX в Console

- Сумма MAX должна вычисляться целочисленно из `pending balance` после
  оценки реальной суммы: `value = balance - gasLimit * gasPrice` для type 0.
- Дополнительный множитель сверх уже увеличенного gasLimit оставляет еще
  больше неизрасходованного остатка. Он может быть сознательным запасом,
  но его нужно показывать как резерв, а не как списанную комиссию.
- Для type 2 upfront учитывает `gasLimit * maxFeePerGas`, а фактическое
  списание - `gasUsed * effectiveGasPrice`. Нельзя сравнивать первое число с
  фактической комиссией type 0 и делать вывод о переплате.
- Фактические комиссии сети меняются с оракулом. Для строгого сравнения с
  официальной Console нужны хеши сопоставимых операций в близких блоках;
  их в этом тесте не предоставлено.
