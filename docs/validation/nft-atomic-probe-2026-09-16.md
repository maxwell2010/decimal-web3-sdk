# Проверка создания коллекции и выпуска NFT одной транзакцией

Дата: 2026-09-16. Только read-only симуляции, без подписей, seed/private key,
загрузок IPFS, разрешений на расход и отправки транзакций. Публичный SDK и Console
не обновлялись. Добавлены отдельный диагностический скрипт и офлайн-тесты.

## Что именно проверено

Запущен `scripts/probe_nft_atomic.py` с официальным RPC
`https://node.decimalchain.com/web3/`, chain ID 75. Данные вызовов создания и выпуска
собраны через `build_unsigned_candy_call` нашего SDK. `aggregate` закодирован
существующим `MULTICALL_ABI` нашего SDK.

Все вызовы привязаны к одному блоку:

- Высота: **33668181**.
- Хеш: `0x702320507148d008ca6459232199d5fc9b56f6b3e8b714f9d3f4ee1c94ffcf3b`.
- Указанный в симуляции публичный кошелёк:
  `0x40900a48273644768C09183E00E43528c17A29f6`.
- NFTCenter: `0x443cc8ac24630be9257483a09c34ffa81608eace`.
- Multicall: `0x7b23eb47587ca6482fc16cb3d9d426ec64d4b5fc`.

`eth_call` исполняет вызовы в временном состоянии EVM и не сохраняет их в сети.
Параметр `from` - только контекст симуляции; подписи этого кошелька нет.

## Результаты

| Сценарий | Создатель - кошелёк пользователя | Создатель - публичный Multicall (НЕБЕЗОПАСНЫЙ контроль) |
| --- | --- | --- |
| DRC721 без резерва | Create + mint отклонены | Получатель имеет 1 NFT, но creator = Multicall |
| DRC721, 0,001 DEL | Create + mint отклонены | 1 NFT, reserve = 10^15, creator = Multicall |
| DRC1155 без резерва, ID 0, 2 копии | Create + mint отклонены | Получатель имеет 2 копии, creator = Multicall |
| DRC1155, ID 0, 2 копии, всего 0,002 DEL | Create + mint отклонены | 2 копии, reserve = 2*10^15, creator = Multicall |

Во всех четырёх сценариях контроль `create + creator() + balanceOf(...)` прошёл:
создатель правильный, баланс NFT равен нулю. Это подтверждает корректность вызова
создания, заранее определённого адреса и порядка операций. После добавления mint
получен RPC revert `{code:3, message:"execution reverted", data:"0x"}`.
Multicall скрывает вложенную причину ошибки своим `require(success)`.

Дополнительный контроль на существующей коллекции TTTEST
`0x9b1129ec66afd4b7d20f95de078126853695ccfe`:

- Прямой mint от её создателя успешно симулирует выпуск ID 1.
- Тот же mint от адреса Multicall отклоняется `OnlyCreator()` (`0x47bc7cc8`).
- **ID 1 не выпущен в сеть этим тестом.**

Адрес новой коллекции в этих симуляциях:
`0xB7eC3815190248BA7E5F2475758738dFDC62b596`. После симуляций `eth_getCode`
по тому же блоку возвращает `0x`. Это временный адрес, не созданная коллекция и
не безопасный адрес для заранее подготовленной реальной транзакции: он зависит
от nonce NFTCenter и может измениться при других созданиях.

## Причина и границы вывода

Проверены опубликованные исходники:

- [Multicall](https://api.decimalchain.com/api/v1/contracts/0x7b23eb47587ca6482fc16cb3d9d426ec64d4b5fc):
  `aggregate` делает обычный `target.call`, не сохраняет исходный `msg.sender`.
- [NFTCenter](https://api.decimalchain.com/api/v1/contracts/0xced55da70f42ab101b4ce10aa9e767607cef5146):
  создание разворачивает и регистрирует коллекцию, без вызова mint.
- [DRC721](https://api.decimalchain.com/api/v1/contracts/0xe0f7399e648a140d8242c98930ee3d0570d3738b):
  mint/mintByDEL/mintByPermit проверяют `onlyCreator`. `_setCreator` является
  внутренним методом и работает только при инициализации; внешней передачи
  creator в проверенном ABI нет.

Назначать creator публичному Multicall нельзя: другие адреса тоже могут вызвать
его aggregate и действовать от имени создателя (например, выпускать дополнительные
NFT или запретить дальнейший выпуск). Успешный mint без проверки creator был бы
ложноположительным результатом теста безопасности.

Вывод ограничен **обычным EOA-кошельком + текущими NFTCenter/Multicall**. Не доказана
невозможность любых атомарных решений: отдельный контролируемый smart-account/router
или изменение фабрики требуют самостоятельной архитектуры, проверки прав и аудита.
В этом исследовании такие контракты не создавались и не подменялись.

ERC20 reserve/permit в свежесозданной коллекции здесь не симулировался. Работоспособный
mintByPermit в существующей коллекции не означает создание новой коллекции вместе
с NFT и не меняет проверку onlyCreator.

## Воспроизведение и защита

```powershell
python scripts/probe_nft_atomic.py --rpc https://node.decimalchain.com/web3/
python -m pytest tests/test_nft_atomic_probe.py tests/test_nft_protocol.py -q
```

Скрипт фиксирует текущий блок при каждом запуске; публичный контрольный кошелёк
и коллекция могут измениться в будущем. Изменившиеся права/баланс/доступность RPC
могут остановить тест и требуют повторного анализа, а не отмены проверок.

В проверенном запуске: 18 `eth_call`, 10 `eth_getCode`, по одному `eth_chainId`,
`eth_blockNumber`, `eth_getBlockByNumber`, `eth_getBalance`; **0 подписей и 0 отправок**.
RPC-обёртка использует жёсткий read-only allowlist. Скрипт не принимает ключ,
`--broadcast` или seed; `.env` не загружается. Ошибки транспорта, pruned state
и ограничения RPC не засчитываются как ожидаемый revert контракта.

Добавлены 20 офлайн-регрессий: запрет отправки/подписания, точное кодирование
четырёх сценариев, сохранение creator, суммы и закреплённого блока, отличение
сетевых ошибок от revert. Новые тесты вместе с NFT-протокольными: **51 passed**.
Полный набор SDK: **380 passed**. Ruff в выбранном Python-окружении отсутствует;
проверка этим линтером не выполнена.

Практический безопасный путь без новых контрактов: единый UX создания и выпуска
с последовательными транзакциями, без ручного перехода между формами. Для выпуска
в существующей коллекции permit может убрать отдельную транзакцию approve, если
резервный токен и кошелёк поддерживают необходимую подпись. Этот UX и permit API
не реализованы и не опубликованы данным исследованием.
